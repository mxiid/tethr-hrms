## Hiring flow: the ten flagged gaps closed (2026-09-15, PR #3)

The hiring-flow ambiguities recorded in [process-flows.md](process-flows.md) are fixed, with one migration (`ApplicationsUniqueActive`) and new consumers; the notes below are the audit trail.

**Lifecycle.** Sending an offer now writes `stage = 'offer'` on the application, and sub-stage facts cascade to the outcome without a second manual update: a shortlist "not interested" or a failed/no-show interview ends the application `rejected`; a declined offer ends it `withdrawn`, a withdrawn offer `rejected`. Cascades are idempotent and never overwrite a `hired` or already-terminal outcome. Putting a hiring request on hold freezes its linked position (`frozen`), and resuming reopens it.

**Intake integrity.** `FormSubmission` has no dead ends: `FormsService` validates `email`-typed fields before a submission is stored, and the projection now records missing-posting-context, missing-posting and invalid-email submissions as `rejected` with a reason. Migration `ApplicationsUniqueActive` adds a partial unique index (`(organizationId, candidateId, jobPostingId) WHERE outcome = 'active'`) after clearing any legacy duplicates, so one open application per person and posting is a database guarantee; intake refuses a duplicate with a reason and a `23505` backstop catches the race, and `updateApplication` refuses reactivating a duplicate. A rejected or withdrawn candidate can still re-apply later as a new row, preserving history.

**Postings and events.** `unpublishJobPosting` is a real mutation, `postingForRequest` reports live state (the request panel gained an Unpublish button), and cancelling or filling a request unpublishes its postings — the live check caught that the board path returned before the unpublish ran, so the home-tenant unpublish now happens after the platform switch unwinds. Both previously dead events have consumers: `employee.created` seeds the seven onboarding tasks (idempotent) and `hiringRequest.updated` (payload now carries the title) sends a Slack notice.

**Hire handoff and visibility.** Acceptance copies the offer's `probationDays` into `probationEndDate` on the employee and records the offered salary as the first `SalaryRevision` (reason `hire`) when the client workspace has an active structure in that currency — skipped otherwise, where payroll readiness still flags `noPayAssignment`. `employeeOnboardingProgress` gives the checklist an aggregate read (completed/total/allComplete, bank details included) and the profile badge says "all done". The CV parse seam is still a deliberate stub, but it is no longer invisible: the application view exposes `cvParse` and the pool shows "Awaiting AI parsing".

**Review round (PR #3).** Greptile and CodeRabbit plus a security pass flagged follow-ups; all are fixed. The lifecycles are now transactional: offer `send/withdraw/decline`, interview `updateStatus` and shortlist `recordDecision` write the sub-stage row and the application cascade in one transaction. Position reconciliation is state-based and idempotent, follows an **existing link by id** (title lookup only links a request that has none, and titles are neither unique nor immutable), and runs on every update so replaying the same status repairs a missed sync — the durable `hiringRequest.updated` consumer reconciles again from the request's workspace on **every** status change (a resume included), taking postings down only for held/terminal states. Automatic unpublish is both immediate (best-effort sync, now skipped inside a caller-owned transaction after a live deadlock exposed that hazard) and durable (the consumer switches to the operator workspace as the system principal and retries via the outbox); `onHold` takes the posting down too, and the panel shows the publication section for `open || onHold`. All posting rows for a request are reconciled in one transaction with their audit records, and legacy duplicates are handled by deterministic reads plus publish/unpublish reconciliation. The offer salary now reaches compensation through a new `offer.accepted` event and an idempotent consumer, removing the synchronous cross-module call; `recordHireSalary` tolerates redelivery and runs its own transaction when no manager is passed. `ApplicationsUniqueActive` is genuinely reversible: it records the rows it rewrites and `down()` drops the index first, then restores outcomes/notes. Small fixes: reactivation races translate to `ConflictError` by constraint name, the duplicate-race catch still records the CV, the email pattern is linear, and the onboarding badge preserves a server-reported total of zero. The second security pass hardened the cross-tenant edges: privileged posting cleanup carries the **operator organization explicitly** (the raw manager query would otherwise match another workspace's posting that happens to share the request id), and offer acceptance fills the **request's linked position by id**, using the title lookup only when no link exists. Synchronization decisions follow the freshest request state throughout — `updateHiringRequest` reconciles and reports the reloaded request (with a bounded convergence re-check), the consumer gates unpublish on the current status and skips a superseded event's notice — so a retried stale held event can neither unpublish a reopened posting nor announce an outdated status. The follow-up pass tightened the transactions themselves: the request status audit now commits **inside** the update transaction (a failed audit rolls the transition back instead of leaving a changed request reported as an error), a position link records its own atomic `linkPosition` audit, and offer `send`/`withdraw`/`decline` take the same pessimistic write lock as acceptance so a concurrent transition cannot overwrite `accepted` after the employee exists. The link itself is a conditional targeted update — only `positionId`, and only while the row is still in the expected state and unlinked — with its `linkPosition` audit in the same transaction, so it can never write a stale status back; the bounded reconciliation also applies the final observed state after its attempt limit instead of returning an unreconciled observation. Acceptance's fallback links **before** filling: when a competing transaction owns the link, the title-resolved position is left untouched and the request's actual linked position is filled instead.

## PR #2 fourth review round: migration safety and transition atomicity (2026-09-15)

The fourth bot pass flagged deploy-safety and atomicity follow-ups; all three are fixed.

**Migration safety.** `Phase2AdjustmentSourceGuard` adds a CHECK that provenance is a pair (`sourceType`/`sourceId` both or neither), but PostgreSQL validates a new CHECK against every existing row — and the old schema and GraphQL input allowed half-pairs. The migration now clears one-sided provenance rows (`UPDATE ... SET "sourceType" = NULL, "sourceId" = NULL WHERE ("sourceType" IS NULL) <> ("sourceId" IS NULL)`) before adding the constraint; the money fact survives and every in-code writer already sets both. Verified end to end on the scratch database: revert → seed a one-sided row → run → the row is normalized and the constraint holds (a mismatched insert is rejected `23514`).

**Snapshot race recovery.** `recordCostSnapshot` is idempotent per run, but its `findOne → save` pair can race (`draftInvoicesFromRun` vs the void refresh on the same run; unique index `payroll_cost_snapshots_org_run_unique`). The loser now catches only `23505`, re-fetches the winner's snapshot by `payrollRunId` and returns it; if the row is still absent it rethrows the original error, and every other error propagates.

**Transition atomicity.** `markInvoicePaid` and `voidInvoice` now read the invoice with an organization-scoped `pessimistic_write` lock, re-check the status inside that transaction, and commit the state change with its audit record (`audit.record(input, manager)`), so a concurrent confirmation conflicts instead of double-applying and a crash cannot leave a paid/voided invoice with no audit. Void's period-close refresh stays idempotent post-commit work, re-triggered by any later draft of the same run.

## Finance Phase 2 / M2: per-employee tax profiles & withholding elections (2026-09-14)

The second confirmed-absent feature is in: withholding is no longer one tenant-wide ladder for everyone. `EmployeeTaxProfile` (compensation module) is an effective-dated fact — filer status, monthly exemption, annual tax credit, prior-employer income, and an optional fixed monthly withholding — with one open profile per employee (partial unique index) and a first profile that starts at hire so the facts apply from day one.

**The calculation.** `calculateMonthlyWithholding` gained an options argument with a defined, explainable method: the monthly exemption reduces the taxable base first, then the amount is annualized and **prior-employer income is removed marginally** (tax on current+prior minus tax on prior — the employee's bands already consumed are not taxed twice), resolved annual credits are subtracted, and the result divides into months. A fixed monthly amount overrides the ladder entirely; a finance line override still beats the fixed amount. No options → byte-identical behavior to before.

**Payroll integration.** Finalization resolves the profile as of the **period being paid** (not the day finalize runs), and the draft preview in `getRunDetail` applies the same facts so finance never sees one number on the draft and another on the payslip. Every payslip snapshots the withholding trail (`taxProfileSnapshot`: source `lineOverride`/`fixed`/`profile`/`computed` plus the facts applied); the GraphQL view exposes `taxProfileSource` + `taxProfileSummary`, and the payslip PDF prints the facts on its computed line. A profile change publishes `compensation.taxProfileChanged`, and a new payroll consumer marks open drafts stale with `Tax profile changed effective <date>`.

**Web.** The employee record's Job & Pay tab gained a Tax profile section: current facts, edit-through-a-modal (with effective date), and the full history. Verification caught a UX gap — future-dated profiles were invisible because the history list skipped the newest row; it now excludes only the profile in force, so upcoming changes show on the record.

## Finance Phase 2 / M1: expense claims & reimbursements (2026-09-14)

The first of the three confirmed-absent features (see finance-plan.md §11) is in: employees file claims with receipts, approval rides the existing workflow engine, and the money reaches people either directly or through the next payroll run — with client-billable lines flowing onto the expenses invoice instead of being retyped.

**The module.** New `modules/expenses` owns `ExpenseCategory` (code, receipt-mandatory, client-billable; six usable defaults seed on first read), `ExpenseClaim` (draft → submitted → approved/rejected → paid, `EXP-####` assigned at submit with a unique index and retry, totals recomputed server-side) and `ExpenseClaimLine` (date, description, amount, receipt facts). Receipt uploads go through signed URLs into a workspace-prefixed key (`expense-receipts/<org>/<date>/…`); attaching one calls `StorageDriver.statObject` to prove the object exists at the claimed size, so a line can't point at an arbitrary bucket object. Self-service actors only ever see their own claims — another employee's claim reads as *not found*.

**Approval & payout.** Submitting opens a workflow approval (`subjectType 'expenseClaim'`) — no second approval mechanism. Reimbursement is explicit: finance marks a claim paid **directly** (reference kept) or **via payroll**, which creates a `PayAdjustment(kind 'reimbursement', sourceType 'expenseClaim')` for a chosen component and period, so the money rides the normal run and the payslip line traces back to the claim. Billable lines push to the client's **draft expenses invoice** through a new billing published method (`addExpenseClaimLines`) that finds-or-opens the month's draft and tags each line `[EXP-####]` so a retry never double-bills; the claim keeps the invoice id.

**Platform scope, corrected mid-build.** The cross-workspace board (`clientExpenseClaims`) and the cross-workspace actions require `platform:read-all` — a Tethr-only operator permission — not `expense:read`; the verification caught that a `clientAdmin` sitting inside the Tethr workspace could otherwise read the board. `tethrFinance` gained `platform:read-all` so it can pay and bill across workspaces, and `sync:role-permissions` backfilled all seven role rows (`expense:read/write/approve/pay/own:*`, client roles get read, clientAdmin gets approve).

**Migration housekeeping.** `Phase2ExpenseClaims` adds the three tables; `Phase2FinanceDefaults` ends a generator quirk where the numeric defaults on `Invoice.subTotal/totalAmount` and `ClientBillingConfig.feeAmount` were re-emitted in every generated migration — the entities now declare plain numeric defaults, and a fresh generate reports *no changes*.

**Verification.** API 20/20 (seeded categories, receipt mandatory refusal, signed upload + `statObject` verification, billable totals, submit→approve→reimburse via a sourced payroll adjustment, client pass-through with marker + duplicate refusal, receipt byte-for-byte download, cross-workspace board + client rejection, employee self-service filing and direct reimbursement). Web 11/11 (Tethr board + approve-from-panel + payout controls + billed-invoice link, client portal without payout controls, employee home filing → submit). Gates: **207 API / 20 shared / 5 UI tests**, lint 0 errors, typecheck/build clean.

## Finance Phase 1: employer cost is first-class, and payroll↔billing actually reconciles (2026-09-14)

**WP1 — employer contributions stop evaporating.** `line-math.ts` now surfaces `employerContributions`/`employerCost` alongside the employee-side totals, and `PayrollRun`/`Payslip` snapshot them (`employerContributionTotal`/`employerCostTotal`; per-payslip `deductionsAmount`/`employerContributionAmount`/`employerCostAmount`). A snapshot whose rate was never configured is recorded and flagged `no_cost_data` rather than guessed.

**WP5 — the correctness sweep.** Service-month derivation now follows the run's own pay date (advance when cut on/after the anchor) instead of the wall clock, so backfills stop skipping months; drafts can be **voided** (partial unique index ignores voided rows, covered-months and the duplicate-draft guard ignore them too) and the released month re-drafts; invoice numbers get a unique index plus a 23505 retry loop, payslip numbers a unique index; issued invoices freeze their letterhead/bank/sender/logo in `issuedSnapshot` so later setup edits cannot rewrite a shipped document; billing memberships inherit `rateCurrency` from the tenant billing config; `markInvoicePaid` accepts a settlement date (the value date, which can lag the day it is recorded); `addInvoiceLine` no longer silently drops `kind`/`employeeId`/`monthLabel` (manual salary lines resolve the name and participate in reconciliation); rate changes flag affected drafts `isStale`; payroll runs (and final settlements) gained mark-paid with paidAt/reference; and the intentionally unconsumed `invoice.issued`/`bonus.awarded` events are documented as integration seams in finance-plan.md §4.

## Code-review fixes on the finance interconnection work (2026-09-11)

An 8-angle review of the Phases 0–4 diff surfaced ten findings; the money/data-integrity ones are fixed, each with a regression test.

- **Final settlement now pays every adjustment kind, taxed like a payslip (findings 1 & 2).** It previously read only `advanceRecovery`, silently dropping bonuses/arrears owed in a leaver's final month, and applied no withholding. `FinalSettlementService.compute` now folds all period `PayAdjustment`s in (earning kinds add, deduction kinds subtract, each pro-rated by its `dependsOnPaymentDays`), computes taxable base, and applies the active tax ladder via the same `calculateMonthlyWithholding` engine as regular runs. New columns: `adjustmentEarnings`, `taxableAmount`, `incomeTaxAmount`, `netPayableAmount`.
- **Billing membership can no longer be double-booked (finding 3).** The effective-dating move dropped the `(org, employee)` unique index and never replaced the overlap rule. Added a Postgres **partial unique index** (`validTo IS NULL`) as the race-proof backstop, plus a service-level `rangesOverlap` guard mirroring `AssignmentService` that returns a clean conflict first.
- **Payroll eligibility has one source (finding 4).** Readiness and draft generation each recomputed eligibility independently and could disagree. Both now derive from one `computePayrollBasis`; the readiness banner and the run are computed from identical facts.
- **`createAdjustment` enforces kind↔category (finding 5).** An `advanceRecovery` on an earning component used to silently add money; earning kinds (`bonus`/`encashment`/`arrear`) must use earning components and `advanceRecovery` a deduction component.
- **Per-employee work is parallel and scoped (finding 6).** The readiness/draft loops were sequential per employee (N+1) and the record's Pay tab triggered a tenant-wide computation. Basis computation now runs under `Promise.all`, and a new `employeePayrollReadiness(employeeId, …)` query computes a single person; the hub uses it.
- **`updateRunLine` no longer double-applies a day delta (finding 9).** When `payableDays` and `lopDays` are edited together, `payableDays` is authoritative and the invariant `payable + unpaid ≤ standard` is kept; the lop delta is applied only when unpaid days are edited alone.
- **Finalize distinguishes a zeroed period from legitimate zero pay (finding 10).** A line with payable days but zero earnings now needs an explicit override (e.g. a bad holiday calendar), while a genuinely idle month (no payable days) still passes.
- **Bank change requests ride the workflow engine (finding 7).** Requests create a generic `ApprovalRequest` (`subjectType 'bankDetailChange'`) and decisions go through `WorkflowService.decide`, so there isn't a second bespoke approval mechanism. (`LeaveRequest` does not itself use the engine today — the shared engine was previously unwired.)
- **`PayAdjustment` is deliberately period-scoped (finding 8, not changed).** It models a specific pay period (`periodYear`/`periodMonth`), matching Frappe's `Additional Salary`/`payroll_date`, not an open-ended effective-dated fact; the recurring mode carries its own half-open window. Documented on the entity.

## Key decisions & deviations

- **npm workspaces over Nx** (architecture.md §15 deviation) — zero-install,
  fully verifiable. TS project-reference-free; packages build in explicit order.
- **Within-package imports are relative; `@/`,`~/` aliases** are wired via
  tsc-alias (build) + jest mapper. Cross-package uses real package names.
- **`@typescript-eslint/consistent-type-imports` is OFF** — it conflicts with
  NestJS constructor injection (its autofix turns DI class imports into
  `import type`, erasing the `emitDecoratorMetadata` reference and breaking DI).
- **Half-open date ranges** `[validFrom, validTo)` so adjacent records neither
  overlap nor gap.
- **GraphQL schema generated in memory** at boot (no filesystem dependency).
- **Vite consumes internal packages from source** (avoids CJS named-export interop).
